# Verify authentication and authorization

Read when planning acceptance checks and again before claiming completion. Select cases for the requested change and actual mechanisms; keep coverage of the full affected flow. A unit test for a helper does not establish a server trust boundary.

## Behavioral evidence

| Area                   | Required evidence when applicable                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Login/current user     | Valid and invalid credentials, anonymous user, minimal authenticated user view, blocked/deleted account, equivalent public failure responses, expired credentials. Real server requests establish identity.                                                                                                                                                      |
| Authorization          | Guest, allowed and forbidden users; resource ownership, cross-tenant/IDOR attempts, forged user/role fields, policy changes and self-escalation. Exercise the protected operation directly, not only UI navigation.                                                                                                                                              |
| Logout                 | Current session/grant revoked, cookies and private client caches cleared, protected requests denied within the documented revocation bound, repeat logout handled, server failure reported honestly. Test immediate denial where promised. Test logout with expired access but a still-valid session/refresh credential, and define treatment of other sessions. |
| Sessions               | Fixation prevented at login/elevation, idle/absolute expiry, revocation and disabled accounts enforced. Test any promised revocation latency rather than assuming logout invalidates all signed tokens instantly.                                                                                                                                                |
| Renewal                | If refresh tokens exist: expiry, rotation, replay detection and revocation behavior, simultaneous refreshes, bounded retry after rejection, no late response restoring a logged-out/switched account. Verify atomic consumption with the real store.                                                                                                             |
| Browser boundary       | Cookie attributes on actual responses; CSRF rejection for protected mutations including login/logout/refresh/linking; credentialed CORS restricted to trusted origins; unsafe return URLs rejected. Test normalization/encoding, protocol-relative URLs, backslashes and control characters.                                                                     |
| OAuth callback         | Success, user cancellation, missing/wrong/expired/replayed state, wrong/missing PKCE verifier, malformed/duplicate callback inputs, code reuse, provider error/timeout and wrong provider/issuer. Direct calls to backend completion cannot bypass correlation.                                                                                                  |
| OIDC/provider identity | Invalid signature/algorithm/audience/time/nonce, mismatched UserInfo subject, missing/changed email, stable subject resolution. Test each configured provider's contract rather than assuming identical claims.                                                                                                                                                  |
| Linking                | Proof of both identities, email collision without automatic merge, identity owned by another user, local-account switch during callback, concurrent linking, last usable login method preserved on unlink.                                                                                                                                                       |
| Recovery               | If changed or affected: generic request responses, expiring single-use challenges, brute-force limits, replay/concurrent consumption, credential update and required revocation committed atomically.                                                                                                                                                            |
| Isolation/failures     | Two different users, SSR requests if present, shared-cache isolation, provider/store failure, missing production config, redacted logs. Errors never fall back to authenticated/privileged access.                                                                                                                                                               |

Use unit tests for policy/validation, API/integration tests for trust boundaries and persistence, and a small end-to-end path for client → server → store → response. Tests that only assert mocked calls or duplicate implementation do not prove behavior.

Provider doubles must cover adverse responses. They do not replace a real callback round trip with authorized test credentials in the named target environment. When that is unavailable, keep the integration gate open and report what was tested locally.

## Environment evidence

Record the target (local container, preview, staging or another explicitly selected environment). Starting a dev process is not evidence for a deployment with a different origin/proxy/cookie setup.

- Start the application and required dependencies using repository procedures; confirm readiness and exercise login, current user, one permitted and one denied resource request, logout, and denial within its documented revocation bound. Record the event that starts that bound and test immediate denial where promised. Use a real browser for cookie/OAuth flows, or the actual client/protocol for API/native flows.
- Check public origin, registered callback, TLS termination, trusted proxy handling, credentialed requests and cookie scope in the target topology. Test the real callback method: cross-site form POST and top-level GET may need different correlation-cookie policies. Do not “fix” callback failures by disabling transaction validation, broadly disabling application CSRF, or removing secure-cookie protections. A library-owned callback can use the narrowly scoped CSRF handling described in the OAuth reference.
- Where several instances exist, verify shared transaction/session/rate-limit storage or another deliberate coordination strategy; test revocation/rotation across instances. For stateless validators, verify issuer/audience, signing-key refresh and the agreed revocation bounds. Do not require a central session database solely because there are multiple services.
- Verify migrations and uniqueness/concurrency behavior against the actual database engine or managed store in an isolated test namespace. Do not reset shared data. Plan schema and credential-format compatibility where existing users/sessions must survive rollout.
- Confirm runtime injection of secret configuration, startup failure for missing required production values, provider registrations and logout destinations. Inspect bundles, logs and tracked changes for accidental credentials without printing secret contents. Public client IDs are not client secrets.
- Use existing Docker/CI paths when present; do not add them solely for this skill. Keep tests outside production and use authorized accounts. Target checks do not imply permission to deploy, change provider registrations, revoke real users' sessions or delete data.

## Completion gates

Report each gate as passed, failed, blocked, or genuinely inapplicable with evidence and a reason. Missing tools/credentials are blocked, not inapplicable.

| Gate                      | What closes it                                                                                                                                            |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Behavioral/security tests | Relevant scenarios above pass, including negative cases at server and persistence boundaries.                                                             |
| Lint                      | Existing repository linter passes for affected packages and required CI scope.                                                                            |
| Typecheck/static analysis | Existing compiler/typecheck/analyzer passes. Identify the language-appropriate command; do not assume TypeScript.                                         |
| Build/package             | Production build passes, or an interpreted stack's actual package/deployment validation passes. No invented compile requirement.                          |
| Runtime                   | App starts, dependencies are ready, affected auth flow is exercised and relevant logs are clean.                                                          |
| Target environment        | Observed auth behavior matches the configured origins, callbacks, TLS, cookies, storage and deployment topology there.                                    |
| Env/documentation         | Safe env examples, configuration validation, provider setup/callback instructions, migrations, access policy and session/revocation behavior are current. |

Find commands in manifests, task runners and CI. TypeScript, PHP, Python and Go projects expose these gates differently; the required outcomes remain the same. A repository with no lint/static-analysis setup has a tooling gap: use a suitable existing project mechanism or propose the minimal appropriate check instead of quietly skipping the gate or adding an unrelated toolchain.

Fix observed failures, then rerun affected checks and required completion gates. If a failure predates the change, report its evidence and scope; do not claim an all-green result. Stop retries that can create accounts, consume one-time codes or mutate external state when the outcome is uncertain. End with exact commands/results, runtime and target evidence, and outstanding blockers. An unverified required gate leaves authentication incomplete.
