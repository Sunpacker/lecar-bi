# План автоматического CI/CD для VPS

## Цель и принятые решения

После успешных проверок изменения в `main` автоматически обновляют работающие на VPS сервисы из [`infra/docker-compose.vps.yml`](../../infra/docker-compose.vps.yml). Сборка выполняется в GitHub Actions, образы `backend` и `notification` публикуются в GHCR с привязкой к полному SHA коммита. VPS получает готовые образы по SSH. Краткий перерыв при обновлении API допустим. Frontend не входит в VPS Compose и в этот деплой не включается.

Автоматическое обновление не должно менять Docker Compose project, имена томов, `infra/.env`, внешнюю сеть Caddy или данные PostgreSQL и Redis. При ошибке после замены контейнеров возвращаются предыдущие образы приложения. Схема БД автоматически не откатывается; условие такого возврата — совместимые расширяющие миграции, описанные в [политике восстановления](backup-and-disaster-recovery.md#5-чистый-запуск-и-стратегия-деплоя).

## Изменения в репозитории

1. Дополнить [CI workflow](../../.github/workflows/ci.yml) выпуском двух образов только для `push` в `main` после успешного job `integration`. Использовать `GITHUB_TOKEN` с минимальными `contents: read` и `packages: write` для публикации в GHCR; метку OCI `org.opencontainers.image.source` связать с репозиторием. Перед SSH-деплоем сверять SHA запуска с текущим `main`, чтобы задержавшийся старый запуск не заменил новый. Запуски деплоя сериализовать без отмены процесса во время миграций.
2. Сделать VPS Compose конфигурацией запуска готовых образов: обязательные `BACKEND_IMAGE` и `NOTIFICATION_IMAGE` без `latest`, без сборки на сервере. Сохранить текущие имена сервисов, сетей и томов. Исправить или убрать команды `make build-vps` и `make vps-up`, которые сейчас собирают локально и ждут readiness до миграций, чтобы они не стали обходным путём мимо новой процедуры.
3. Добавить отдельный серверный скрипт деплоя с явными параметрами `release SHA`, `release directory`, `Compose project` и путём к серверному env-файлу. Он принимает только ожидаемые образы из GHCR, фиксирует SHA и digest обоих образов, использует блокировку `flock`, сохраняет предыдущий успешный релиз и делает повторный запуск того же SHA безопасным. В каталог каждого релиза включить `infra/docker-compose.vps.yml` и дерево `infra/observability/`: Compose использует относительные bind mounts для мониторинга. Секретный `infra/.env` хранить вне каталогов релизов и Git.
4. Адаптировать резервное копирование для VPS Compose: обе БД, явные имя проекта и env-файл, проверки успешности `pg_dump` и целостности gzip до миграций. Текущий [`scripts/backup-db.sh`](../../scripts/backup-db.sh) жёстко использует dev Compose и поэтому не подходит без изменений. Бэкапы сохранять вне релизов; не удалять их при обычной очистке Docker-образов.
5. Документировать первоначальное подключение и ручное восстановление в [`infra/README.md`](../../infra/README.md): доступ SSH для отдельного пользователя деплоя, Docker Compose v2, доступ к существующей внешней сети `proxy`, переменные и секреты GitHub, доступ VPS к GHCR, путь установки, проверки и откат. Для приватных образов на VPS использовать отдельный токен только с `read:packages`, хранящийся на сервере; токен публикации остаётся временным `GITHUB_TOKEN` workflow. Адрес, SSH-порт и путь установки задавать как параметры окружения GitHub, а не прошивать в скриптах.

## Порядок одного деплоя

1. До первого запуска выяснить на VPS фактическое значение `COMPOSE_PROJECT_NAME`, текущие image ID контейнеров и имена томов. Зафиксировать существующую установку как исходный релиз для возможного возврата. Если project или тома не совпадают с ожидаемыми, остановить подготовку до выяснения причины.
2. CI проверяет код, собирает и публикует оба образа для одного SHA, передаёт на VPS релизный пакет и его SHA, проверяет доступность GHCR, Docker, внешней сети, конфигурации Compose и обязательных секретов до остановки приложений. Получить оба образа и проверить их digest.
3. На VPS под блокировкой создать и проверить резервные копии обеих БД. Остановить только `backend`, `notification` и `notification-worker`; PostgreSQL, Redis и мониторинг продолжают работать. Выполнить миграции обеих БД одноразовыми контейнерами новых образов без запуска новых постоянных сервисов.
4. Поднять три приложения с новыми образами и дождаться `healthy` с ограниченным таймаутом. Проверить публичный endpoint `https://api.veloza.ru/lecar-bi/api/v1/health`, readiness уведомлений и новый heartbeat `notification-worker`, записанный после запуска новой версии; старое значение в Redis не должно считаться успехом. Проверить отсутствие цикла перезапуска контейнеров. Только после этих проверок пометить релиз успешным.
5. При ошибке бэкапа не останавливать сервисы. При ошибке миграции или проверок вернуть образы предыдущего релиза, снова проверить сервисы и завершить workflow с ошибкой. Не запускать автоматически `migrate:rollback` и восстановление баз из резервной копии. Если предыдущий релиз недоступен либо восстановление приложения не прошло, сохранить диагностику в логе и передать восстановление оператору.

## Проверка перед включением автоматики

- Проверить конфигурацию Compose и shell-скрипты без доступа к боевым данным; выполнить CI, сборку контейнеров и тест чистых миграций.
- На копии окружения проверить успешный выпуск, повторный запуск того же SHA, сохранение существующих томов, отказ бэкапа, сбой миграции, нездоровый backend, остановившийся worker, устаревший heartbeat и параллельные запуски.
- Перед первым реальным обновлением вручную сверить имя Compose project и тома, проверить наличие двух пригодных бэкапов и исходного релиза. После обновления подтвердить публичный health endpoint, готовность уведомлений, живой worker и работу Caddy.

Первый реальный деплой и добавление SSH/GHCR доступа выполняются после получения адреса VPS, SSH-порта и каталога действующей установки. Эти значения не влияют на кодовую схему и остаются параметрами настройки.
