# Phase 17 — Observability

[Roadmap index and rules](ROADMAP.md) · [Agent router](../../AGENTS.md) · [Infrastructure architecture](../architecture/09-infrastructure-deployment-observability.md)

## Goal

Use a single user request or `event_id` to find related events across frontend, analytics, outbox, and notification; see the state of HTTP services, workers, and imports; receive an operational signal before a user discovers the problem.

This phase follows [Phase 16](16-performance-caching.md). Product rules and incidents from [Phase 12](12-alerting.md) remain separate from operational alerts.

## Initial State

- `frontend` already provides `GET /api/health`; analytics provides `GET /api/v1/health` with a static response and no dependency checks.
- Notification provides `GET /api/v1/health/live` and `/ready`; readiness checks its own PostgreSQL and Redis, but not `notification-worker` state.
- Analytics/notification HTTP and worker processes run separately. The integration event already contains `event_id`; an end-to-end request identifier and trace context are not yet part of its contract.
- Service logs go to stderr; a centralized collection, metrics, and dashboard stack has not yet been deployed.

## Target Stack

For local and production-like Docker environments: **Grafana** for dashboards and operational alerts, **Prometheus** for metrics, **Loki** for logs, and **Grafana Alloy** for container log collection. Store data source, dashboard, and rule configuration in the repository; pin images to compatible versions, without `latest`. Give stores separate volumes and bounded retention. Restrict Grafana, Prometheus, Loki, and technical endpoint access to the internal network or administrators; do not expose them as user-facing APIs.

This is the phase's baseline stack. Use **OpenTelemetry** as the context standard and expansion path toward traces. Add **Tempo** only alongside real instrumentation and an end-to-end trace viewing scenario; an empty trace backend is not part of the completion criteria. A separate **Sentry** is optional: first establish error diagnostics through structured logs, metrics, and Grafana. Do not introduce a second alerting channel or a new broker for observability.

## Implementation Sequence

1. **Context and logs.** Generate or validate `request_id` at the trust boundary; propagate it in server-side Next.js → analytics calls and return it in responses for diagnostics. Handle direct browser-to-analytics calls separately: they do not pass through the Next.js HTTP process. Add a unified JSON log format with time, level, service name, environment, operation/route template, `request_id`, and error code. For jobs, outbox, and notification, record `job_id`/`event_id`, attempt, and result; where needed, carry `correlation_id` from the original request through the queue and versioned event envelope with a compatible [event contract](../../contracts/events/alert-triggered.v1.schema.json) change. Clear context between jobs in long-lived workers. Do not log tokens, import contents, personal data, or full event payloads. Keep `request_id`, `event_id`, and `trace_id` as log fields, not Loki labels.
2. **Health and worker signals.** Separate liveness (the process accepts requests) from readiness (only necessary local dependencies) for HTTP services; replace analytics' static response with verifiable readiness, preserving compatibility of the current `GET /api/v1/health` and updating OpenAPI/client if the contract changes. Do not include dependencies on other deployable services in readiness. Measure `notification-worker`, queue, and outbox health separately through heartbeats, age of last successful processing, and task accumulation; a live HTTP process does not imply a live worker.
3. **Signal collection.** Connect Alloy → Loki for container stdout/stderr and Prometheus for scraping internal metrics endpoints/exporters. Provide HTTP rate/error/latency metrics by route template, job/import duration and outcome, outbox backlog and age, Redis Stream consumer group/pending and dead-letter state, worker heartbeat freshness, dependency availability, and target `up`. The worker metrics source must account for separate processes and restarts; metrics held only in HTTP process memory do not cover workers. Use low-cardinality labels (`service`, `environment`, `route`, `result`); do not include parameterized URLs, user/workspace IDs, or event identifiers.
4. **Dashboards and responses.** Provision Grafana: service overview (availability, HTTP errors, and latency), background processes (jobs, imports, outbox, stream lag/dead-letter), and log search by identifier. Add operational rules for unavailable targets/readiness, missing worker heartbeat, growing backlog/old outbox messages, dead-letter, and sustained error increases. Specify thresholds, evaluation windows, `No Data`/data source error behavior, recipient, and runbook for each rule; verify test triggering and recovery. Configure the notification channel through environment secrets, without addresses or tokens in Git.
5. **Tracing as needed.** Preserve W3C `traceparent` support at HTTP boundaries, but do not treat `request_id` as a complete distributed trace. If manual log searches do not explain inter-service latency, add OpenTelemetry instrumentation → Alloy/OTLP → Tempo for the specific `frontend → analytics → outbox → notification` path; configure sampling and exclude sensitive attributes. Record the decision to enable Tempo and its operational costs during implementation.

When implementing the stack, update the [infrastructure architecture](../architecture/09-infrastructure-deployment-observability.md) and an ADR if the choice becomes a lasting architectural decision. Infrastructure adapters must not add dependencies to the Domain Layer.

## Exit Criteria

- One test server-side frontend → analytics call can be found by `request_id` in both services' logs. A separate event publication scenario can be found by `event_id` in outbox and notification, including redelivery; if initiated by an HTTP request, its link to the original `request_id` is visible. For direct browser-to-analytics requests, the diagnostic `request_id` is visible in the response and analytics logs. Background events are explicitly allowed to have no originating HTTP request.
- Liveness and readiness distinguish a running process from an unavailable local dependency; worker failure is visible separately. Normal startup, temporary PostgreSQL/Redis loss, and recovery verified.
- After a clean startup, Grafana automatically receives data sources, dashboards, and rules; they display real HTTP, job/import, and outbox/notification signals, not just sample data. Logs are available in Loki and can be filtered by service and identifier.
- Prometheus targets are available; metrics remain correct after process restarts. At least one operational alert trigger, delivery, and recovery verified, along with `No Data` behavior.
- Absence of sensitive data and high-cardinality labels in logs/metrics verified; technical endpoints are not publicly accessible. Startup, retention, failure diagnosis, and basic actions for each rule documented.
- [Integration checkpoint](ROADMAP.md#integration-checkpoints) passed: applicable tests, contract checks if health/event APIs change, build, stack configuration, and an end-to-end diagnostic scenario. Mark the phase complete in the index only after these checks.
