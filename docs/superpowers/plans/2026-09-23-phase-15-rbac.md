# Phase 15 — Workspace RBAC Implementation Plan

**Статус:** планирование завершено, реализация не начата.

**Цель:** ввести предсказуемый workspace-scoped RBAC для dashboard, import и alert actions так, чтобы Laravel оставался единственным источником авторизации, а Next.js только отражал разрешённые возможности в интерфейсе.

**Архитектура:** существующая модель членства `owner/member` расширяется ролью `viewer`. Роли принадлежат bounded context `Workspace`, а доступ выражается небольшим закрытым набором capabilities. Backend вычисляет capabilities из роли, проверяет их на HTTP-границе до запуска use case и возвращает effective capabilities в workspace API. Frontend не сопоставляет роли с действиями самостоятельно и не считается security boundary.

**Spec:** [Phase 15 — RBAC](../../roadmap/15-rbac.md), [Frontend Architecture](../../architecture/03-frontend-nextjs.md), [Laravel DDD](../../architecture/04-backend-laravel-ddd.md), [Bounded Contexts](../../architecture/05-bounded-contexts.md), [API and Integration](../../architecture/07-api-and-integration.md), [Testing and Quality](../../architecture/10-testing-and-quality.md), [Architecture Decisions](../../architecture/12-architecture-decisions.md).

### Текущий baseline на момент планирования

- `Workspace` уже хранит membership с ролями `owner/member` и изолирует workspace по `userId`.
- `WorkspaceAccessGuard` проверяет только факт членства, но не разрешённое действие.
- Dashboard, import и alert routes находятся под authentication и membership boundary, но mutations не различают `owner/member`.
- `WorkspaceResponse` возвращает роль, но не возвращает effective capabilities.
- Frontend показывает mutation controls всем участникам workspace.

## 2. Scope

### В scope

- workspace roles `owner`, `member`, `viewer`;
- централизованное сопоставление role -> capabilities на backend;
- effective capabilities в workspace API;
- просмотр участников workspace и изменение роли существующего участника;
- инвариант хотя бы одного `owner` в каждом workspace;
- backend enforcement для dashboard, saved view, import и alert actions;
- capability-aware UI для тех же действий;
- тестирование смены роли и сохранение cross-workspace isolation;
- forward-only ограничение допустимых ролей в PostgreSQL;
- документация матрицы доступа и integration checkpoint.

### Вне scope

- приглашение, удаление и деактивация участников;
- custom roles, UI-конструктор permissions и per-user overrides;
- ownership отдельных dashboard, alert rules или import batches;
- field-level и row-level permissions внутри одного workspace;
- замена текущей identity/session strategy и заголовка `X-User-Id`;
- SSO, OAuth/OIDC, API keys и service accounts;
- авторизация внутренних scheduler/queue jobs через пользовательские роли;
- RBAC внутри Notification Service;
- audit log смены ролей — его следует проектировать вместе с observability/production hardening, а не имитировать обычным application log.

## 3. Зафиксированная модель доступа

### Роли

| Роль | Назначение |
|---|---|
| `owner` | Полный operational access и управление ролями участников workspace. |
| `member` | Работа с аналитическими ресурсами без управления доступом. Существующая роль сохраняется без переименования и миграции данных. |
| `viewer` | Только чтение аналитики и ресурсов workspace. |

Не переименовывать `member` в `editor` или `analyst`: это не даёт продуктовой функции, но создаёт breaking change в API, seed data и persisted memberships.

### Capabilities

| Capability | `owner` | `member` | `viewer` |
|---|:---:|:---:|:---:|
| `analytics.view` | ✓ | ✓ | ✓ |
| `dashboards.view` | ✓ | ✓ | ✓ |
| `dashboards.manage` | ✓ | ✓ | — |
| `imports.view` | ✓ | ✓ | ✓ |
| `imports.manage` | ✓ | ✓ | — |
| `alerts.view` | ✓ | ✓ | ✓ |
| `alerts.manage` | ✓ | ✓ | — |
| `workspace.members.manage` | ✓ | — | — |

Capabilities — стабильная frontend/API граница. Роли — способ их назначения. UI проверяет capability string, а не `role === 'owner'`.

### Route policy

| HTTP actions | Required capability |
|---|---|
| Sales, inventory и supplier analytics `GET` | `analytics.view` |
| Dashboard и saved view `GET` | `dashboards.view` |
| Dashboard и saved view `POST/PUT/DELETE` | `dashboards.manage` |
| Import batch/failure `GET` | `imports.view` |
| Import upload и retry `POST` | `imports.manage` |
| Alert, summary и alert rule `GET` | `alerts.view` |
| Alert rule create/update/delete/toggle/evaluate | `alerts.manage` |
| Alert acknowledge/resolve | `alerts.manage` |
| Workspace member list и role change | `workspace.members.manage` |

`GET /me`, список доступных workspaces и получение current workspace остаются membership-scoped: они нужны для установления самого контекста доступа.

### Error semantics

| Ситуация | HTTP | Code |
|---|---:|---|
| Нет authenticated identity | 401 | `UNAUTHENTICATED` |
| Пользователь не состоит в workspace | 403 | `FORBIDDEN` |
| Член workspace не имеет capability | 403 | `INSUFFICIENT_CAPABILITY` |
| Участник не найден внутри доступного workspace | 404 | `WORKSPACE_MEMBER_NOT_FOUND` |
| Попытка удалить последнего owner через смену роли | 409 | `LAST_WORKSPACE_OWNER` |
| Неизвестная роль | 422 | `VALIDATION_ERROR` |

Cross-workspace запрос не должен раскрывать роль, capabilities или список участников чужого workspace.

## 4. Публичный контракт

### Изменения OpenAPI

`WorkspaceResponse` сохраняет существующие поля и получает обязательный `capabilities: WorkspaceCapability[]`. Поле `role` расширяется с `owner/member` до `owner/member/viewer`.

Добавить schemas:

- `WorkspaceRole`: `owner | member | viewer`;
- `WorkspaceCapability`: enum из восьми значений матрицы;
- `WorkspaceMemberResponse`: `user`, `role`;
- `WorkspaceMemberListResponse`: `items`;
- `ChangeWorkspaceMemberRoleRequest`: `role`;
- `ChangeWorkspaceMemberRoleResponse`: `member`.

Добавить endpoints:

- `GET /workspaces/{workspaceId}/members`;
- `PATCH /workspaces/{workspaceId}/members/{userId}/role`.

На защищённых operations зафиксировать required capability через `x-required-capability`. Расширение используется как проверяемая документация; runtime не генерируется из YAML.

### Role change semantics

- endpoint меняет только существующее membership;
- повторное назначение текущей роли идемпотентно и возвращает `200`;
- owner может изменить собственную роль, только если после изменения остаётся другой owner;
- повышение `member/viewer` до `owner` допустимо;
- `owner` не может обойти cross-workspace boundary;
- после успешного изменения следующий ответ current workspace содержит новую роль и новый набор capabilities;
- frontend после изменения собственной роли выполняет server refresh и больше не показывает недоступные controls.

## 5. Последовательность реализации

### Порядок, ownership и handoff

- Task 1 выполняется интегратором последовательно и замораживает общий OpenAPI contract.
- Tasks 2–4 принадлежат одному backend owner: одновременно менять Workspace Domain и persistence разным исполнителям нельзя.
- После contract freeze Task 6 можно вести параллельно с Tasks 2–5, если generated schema уже зафиксирована и write scopes не пересекаются.
- `backend/routes/api.php`, `backend/app/Providers/AppServiceProvider.php`, `backend/bootstrap/app.php`, OpenAPI и generated client остаются integration-owned high-conflict files.
- Task 7 начинается после готовности capability provider и backend route policy.
- Task 8 и финальный review выполняются после объединения всех частей; roadmap index меняет только интегратор.
- Каждый handoff содержит выполненные проверки, непроверенные команды, изменившиеся routes/contracts и известные расхождения с этим планом.

## 6. Integration Checkpoint

Перед закрытием Phase 15 проверить один связный сценарий на реальном PostgreSQL и HTTP boundary:

1. Owner получает current workspace с полным capabilities list.
2. Owner видит список участников и назначает существующему member роль `viewer`.
3. Новый viewer по прямому HTTP запросу читает dashboard/import/alert data.
4. Тот же viewer получает `403 INSUFFICIENT_CAPABILITY` на dashboard update, import upload/retry и alert mutation.
5. После назначения обратно `member` те же operational mutations разрешены.
6. Member не может читать member list или менять роль.
7. Попытка sole owner понизить себя возвращает `409 LAST_WORKSPACE_OWNER`.
8. Пользователь любой роли не получает доступ к чужому workspace.
9. Frontend после server refresh показывает controls в соответствии с effective capabilities.
10. OpenAPI, generated client, Laravel routes и feature-test matrix содержат одинаковые capability requirements.

Checkpoint считается проваленным, если UI выглядит корректно, но прямой HTTP mutation от viewer проходит.
