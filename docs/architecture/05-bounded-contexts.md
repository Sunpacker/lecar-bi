# 05. Bounded Contexts

## Общий принцип

Backend разделяется на bounded contexts, каждый из которых отвечает за отдельную область предметной модели.

Bounded context должен иметь:

- собственную терминологию;
- чёткую ответственность;
- внутреннюю модель;
- публичные способы взаимодействия с другими контекстами;
- минимальное знание о внутреннем устройстве соседних модулей.

## Начальные bounded contexts

### Workspace

Отвечает за организационную область пользователя и владение ресурсами.

В перспективе может включать:

- рабочие пространства;
- принадлежность пользователей;
- настройки организации;
- ограничения доступа.

### Data Ingestion

Отвечает за поступление данных в систему.

Основные задачи:

- импорт наборов данных;
- валидация;
- staging;
- отслеживание статусов;
- нормализация;
- инициирование построения аналитических проекций.

### Sales Analytics

Отвечает за:

- метрики продаж;
- выручку;
- заказы;
- средний чек;
- тренды;
- аналитику по категориям;
- аналитику по регионам;
- детализацию показателей.

### Inventory Analytics

Отвечает за:

- остатки;
- days of stock;
- дефицит;
- overstock;
- оборачиваемость;
- ABC/XYZ;
- аналитические срезы по складам и товарам.

### Supplier Analytics

Отвечает за:

- эффективность поставщиков;
- сроки поставок;
- процент задержек;
- полноту поставок;
- качество поставок;
- сравнительную аналитику.

### Dashboard

Отвечает за пользовательские dashboard.

Основные задачи:

- создание dashboard;
- изменение dashboard;
- расположение widgets;
- сохранение конфигураций;
- работу с фильтрами;
- владение пользовательскими представлениями.

### Alerting

Отвечает за:

- правила уведомлений;
- вычисление условий;
- создание alert;
- жизненный цикл alert;
- взаимодействие с будущими notification-сервисами.

## Правила взаимодействия контекстов

Один bounded context не должен напрямую использовать внутренние модели другого.

Взаимодействие должно происходить через:

- application contracts;
- публичные сервисы;
- события;
- read models;
- интеграционные интерфейсы.

## Выделение в отдельный сервис

Bounded context может стать отдельным микросервисом, если появляются:

- отдельная нагрузка;
- отдельная команда;
- отдельный жизненный цикл;
- отдельные технологические требования;
- устойчивая доменная граница;
- необходимость независимого масштабирования.
