# 05. Bounded Contexts

## Общий принцип

Backend разделяется на bounded contexts, каждый из которых отвечает за отдельную область предметной модели.

Bounded context должен иметь:

- собственную терминологию;
- чёткую ответственность;
- внутреннюю модель;
- публичные способы взаимодействия с другими контекстами;
- минимальное знание о внутреннем устройстве соседних модулей.

## Начальные bounded contexts

### Workspace

Отвечает за организационную область пользователя, владение ресурсами и разграничение доступа (RBAC).

Основные концепции:

- **Рабочие пространства:** изолированные тенанты (`WorkspaceId`, `slug`, `name`).
- **Ролевая модель:** фиксированный набор ролей (`owner`, `member`, `viewer`), хранящийся в таблице `workspace_members`.
- **Инвариант агрегата Workspace:** в рабочем пространстве обязан оставаться хотя бы один активный владелец (`owner`). Попытка понизить роль последнего владельца блокируется на уровне доменной логики и транзакционной блокировки агрегата (`LastWorkspaceOwnerException` → HTTP `409 LAST_WORKSPACE_OWNER`).
- **Система возможностей (Capabilities):** чистое доменное сопоставление роли замкнутому набору из 8 атомарных прав:
  - `owner`: все 8 прав, включая `workspace.members.manage`;
  - `member`: операционные права (`analytics.view`, `dashboards.view`, `dashboards.manage`, `imports.view`, `imports.manage`, `alerts.view`, `alerts.manage`), без управления участниками;
  - `viewer`: только права на чтение (`analytics.view`, `dashboards.view`, `imports.view`, `alerts.view`).
- **CQRS-операции:**
  - Commands: `ChangeWorkspaceMemberRoleCommand` (с транзакционным локом строки воркспейса для предотвращения race condition).
  - Queries: `GetWorkspaceMembersQuery`, `GetCurrentWorkspaceQuery`, `GetAccessibleWorkspacesQuery`.
- **Централизованный Guard:** `WorkspaceAccessGuard` проверяет членство и наличие требуемой capability для входящего запроса.

### Data Ingestion

Отвечает за поступление данных в систему.

Основные задачи:

- импорт наборов данных;
- валидация;
- staging;
- отслеживание статусов;
- нормализация;
- инициирование построения аналитических проекций.

### Sales Analytics

Отвечает за:

- метрики продаж;
- выручку;
- заказы;
- средний чек;
- тренды;
- аналитику по категориям;
- аналитику по регионам;
- детализацию показателей.

### Inventory Analytics

Отвечает за:

- остатки;
- days of stock;
- дефицит;
- overstock;
- оборачиваемость;
- ABC/XYZ;
- аналитические срезы по складам и товарам.

### Supplier Analytics

Отвечает за:

- эффективность поставщиков;
- сроки поставок;
- процент задержек;
- полноту поставок;
- качество поставок;
- сравнительную аналитику.

### Dashboard

Отвечает за пользовательские dashboard.

Основные задачи:

- создание dashboard;
- изменение dashboard;
- расположение widgets;
- сохранение конфигураций;
- работу с фильтрами;
- владение пользовательскими представлениями.

### Alerting

Отвечает за:

- правила уведомлений;
- вычисление условий;
- создание alert;
- жизненный цикл alert;
- взаимодействие с будущими notification-сервисами.

## Планируемые contexts поддержки

Для будущего RAG-чата предусмотрены `Support` (диалоги, генерации, feedback и orchestration)
и `KnowledgeBase` (источники, индексация и retrieval) внутри analytics-service.
Их контракт и границы определены в [спецификации RAG](rag-support-chat.md) и
[ADR-019](12-architecture-decisions.md#adr-019--rag-support-chat).

Это целевой дизайн, а не описание реализованных модулей. При реализации Workspace расширяется
capability `support.use` для всех существующих ролей; текущий набор из 8 прав выше остаётся
описанием действующего RBAC. Доступ к переписке дополнительно ограничен владением диалогом.

## Правила взаимодействия контекстов

Один bounded context не должен напрямую использовать внутренние модели другого.

Взаимодействие должно происходить через:

- application contracts;
- публичные сервисы;
- события;
- read models;
- интеграционные интерфейсы.

## Выделение в отдельный сервис

Bounded context может стать отдельным микросервисом, если появляются:

- отдельная нагрузка;
- отдельная команда;
- отдельный жизненный цикл;
- отдельные технологические требования;
- устойчивая доменная граница;
- необходимость независимого масштабирования.
